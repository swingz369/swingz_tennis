## Bug 1 — KRITISCH: `actor_id` fehlt im Webhook-Audit-INSERT → Idempotenz funktioniert nie

**Datei:** `app/api/webhooks/booking-completed/route.ts` Zeile 320–337

**Problem:** `auditPayload` enthält kein `actor_id`-Feld. `audit_logs.actor_id` ist `uuid NOT NULL` (schema.ts:401). Jeder INSERT schlägt mit NOT-NULL-Constraint fehl → der Idempotenz-Datensatz wird nie gespeichert → Hardware (Tür/Licht) wird bei jedem Retry erneut ausgelöst.

**Fix:**
1. Booking-Besitzer per `payload.booking_id` aus der `bookings`-Tabelle laden
2. `actor_id: booking.user_id` ins `auditPayload` einfügen

```ts
// Nach Schritt 6 (Hardware-Dispatch), vor Schritt 7 (Audit-Insert):
const { data: booking } = await supabase
  .from('bookings')
  .select('user_id')
  .eq('id', payload.booking_id)
  .maybeSingle();

const auditPayload = {
  actor_id: booking?.user_id,   // Booking-Besitzer als Actor
  action: 'hardware_webhook_trigger' as const,
  resource_type: 'booking' as const,
  resource_id: payload.booking_id, // ← auch Bug 2 behebt das
  details: { ...bisherige details... },
};
```

## Bug 2 — KRITISCH: `idempotency_key` (beliebiger String) in UUID-Spalte → PostgreSQL-Fehler → 503

**Datei:** `app/api/webhooks/booking-completed/route.ts` Zeilen 77, 238, 323

**Problem:** `idempotency_key` wird als `z.string().min(1).max(255)` validiert (kein UUID-Check). `audit_logs.resource_id` ist `uuid NOT NULL`. Jeder nicht-UUID-Key (z.B. `"booking-2024-001"`) erzeugt beim SELECT/INSERT einen PostgreSQL-Fehler → `dedupQueryError` → 503 auf jeden Aufruf.

**Fix — kombiniert mit Bug 1:** `resource_id` auf `payload.booking_id` (bereits UUID) ändern, Idempotenz über `booking_id + event_type` abbilden:

```ts
// Dedup-Query (Zeile 234–239):
.eq('action', `hardware_webhook_${payload.event_type}`)
.eq('resource_id', payload.booking_id)

// Audit-Insert action + resource_id:
action: `hardware_webhook_${payload.event_type}`,
resource_id: payload.booking_id,
```

Alternativ (minimaler Fix): Zod-Schema auf UUID einschränken:
```ts
idempotency_key: z.string().uuid(),
```

## Bug 3 — HOCH: Stripe-Mitgliederzählung ohne Rollenfilter → Overbilling

**Datei:** `app/api/clubs/[id]/stripe-sync/route.ts` Zeilen 137–141
**Auch:** `src/application/services/member.service.ts` Zeile 350

**Problem:** Die Count-Query zählt alle `is_active=true`-Mitgliedschaften — auch Trainer und Admins. Ein Club mit 100 Mitgliedern + 5 Trainern + 2 Admins wird für 107 Seats abgerechnet.

**Fix:** `.eq('role', 'member')` ergänzen:
```ts
// stripe-sync/route.ts (Zeile 139–141):
.eq('club_id', clubId)
.eq('is_active', true)
.eq('role', 'member');  // ← NEU

// member.service.ts — getActiveMemberCount() (Zeile 350):
let q = db.from('user_club_memberships')
  .select('id', { count: 'exact', head: true })
  .eq('is_active', true)
  .eq('role', 'member');  // ← NEU
```

## Bug 4 — HOCH: Owner dauerhaft von Smart-Court-Seite ausgesperrt

**Datei:** `app/(protected)/admin/smart-court/page.tsx` Zeile 78

**Problem:** Owner haben laut CLAUDE.md keine `club_id` in `user_club_memberships`. Die Membership-Query gibt eine Zeile mit `club_id=null` zurück. Der Guard `if (!membership?.club_id)` löst immer aus → Redirect zu `/admin/dashboard?reason=admin_only`.

**Fix (kombiniert mit Bug 5):** Gesamte Auth-Logik durch `requireAuth()` + `requireAdminClub()` ersetzen:

```ts
import { requireAuth } from '@/lib/auth';
import { requireAdminClub } from '@/lib/admin-context';
import { createClient } from '@/lib/supabase/server';

export default async function SmartCourtPage() {
  const { user } = await requireAuth();
  const { clubId } = await requireAdminClub();
  const supabase = createClient();

  const [{ data: club }, { data: courts }] = await Promise.all([
    supabase.from('clubs').select('features').eq('id', clubId).maybeSingle(),
    supabase.from('courts').select('id, name, court_type_id, is_active')
      .eq('club_id', clubId).order('name', { ascending: true }),
  ]);
  // ... Rest bleibt gleich
}
```

## Bug 5 — HOCH: Superadmin sieht falschen Club (ADMIN_CLUB_COOKIE ignoriert)

**Datei:** `app/(protected)/admin/smart-court/page.tsx` Zeilen 29–83

**Problem:** Die Seite erstellt einen eigenen Supabase-Client (`createServerClient` direkt aus `@supabase/ssr`) und macht eine rohe Membership-Query ohne `requireAdminClub()`. Der `ADMIN_CLUB_COOKIE` (gesetzt vom Club-Switcher für Superadmins) wird nicht ausgelesen → Superadmin sieht Daten des ersten DB-Eintrags, nicht des ausgewählten Clubs.

**Fix:** Identisch mit Bug 4 — `requireAuth()` + `requireAdminClub()` + `createClient()` aus den Projekt-Wrappern verwenden. Dadurch werden auch 3 CLAUDE.md-Verstöße behoben:
- `createServerClient` direkt aus `@supabase/ssr` → soll `createClient()` aus `@/lib/supabase/server` sein
- Manuelle Auth statt `requireAuth()` aus `@/lib/auth`
- Manuelle Membership-Query statt `requireAdminClub()` aus `@/lib/admin-context`

## Bug 6 — MITTEL: Stripe-Sync `.catch()` mappt alle Exceptions auf 401

**Datei:** `app/api/clubs/[id]/stripe-sync/route.ts` Zeilen 197–203

**Problem:** Der `.catch()` am Ende der `withApiAuth`-Callback unterscheidet nicht zwischen Auth-Fehlern und anderen Exceptions. Wenn `stripe()` wirft (z.B. `STRIPE_SECRET_KEY not configured`), kommt HTTP 401 statt 500 zurück. Monitoring/Alerting auf 4xx klassifiziert Infra-Fehler falsch; Admin-UI leitet fälschlicherweise zum Login weiter.

**Fix:**
```ts
// Zeilen 197–203 — war:
}).catch((err) => {
  if (err instanceof NextResponse) return err;
  log.error('Unerwarteter Fehler', err instanceof Error ? err : undefined);
  return unauthorizedResponse(err instanceof Error ? err.message : 'Authentifizierung fehlgeschlagen');
});

// neu:
}).catch((err) => {
  if (err instanceof NextResponse) return err;
  log.error('Unerwarteter Fehler in stripe-sync', err instanceof Error ? err : undefined);
  return NextResponse.json({ error: 'Interner Fehler' }, { status: 500 });
});
```

## Bug 7 — MITTEL (latent): `lockResult?.error !== null` ist `true` wenn `lockResult === null`

**Datei:** `app/api/webhooks/booking-completed/route.ts` Zeile 349

**Problem:** `null?.error` ergibt `undefined`. `undefined !== null` ist `true`. Wenn ein zukünftiger Event-Type weder `lock` noch `unlock` in `buildActionsForVendor` hat, bleibt `lockResult = null` und `lockErrored` wird fälschlicherweise `true` → false 207-Antwort, obwohl kein Hardware-Fehler vorlag.

**Fix:**
```ts
// Zeile 349 — war:
const lockErrored = lockResult?.error !== null;

// neu:
const lockErrored = lockResult !== null && lockResult.error !== null;
```

## Bug 8 — NIEDRIG: NaN besteht `contractedHourlyRate`-Validierung → silent data loss

**Datei:** `app/api/trainer-profiles/[id]/route.ts` Zeilen 98–103
**Auch:** Zeilen 108–110 (gleiche Lücke bei `rawExtraRate`)

**Problem:** `typeof NaN === 'number'` ist `true` und `NaN < 0` ist `false`, daher passiert NaN die Validierung. NaN wird in die DB geschrieben; beim nächsten Lesen gibt `parseNumericField(NaN)` `null` zurück → Admin sieht „Nicht festgelegt" obwohl er einen Wert gesetzt hat. (Nicht via normalem Browser erreichbar, da `JSON.stringify(NaN) → null`; relevant für programmatische API-Aufrufe.)

**Fix:** `Number.isFinite`-Check ergänzen (an beiden Stellen):
```ts
// contractedHourlyRate (Zeilen 98–103):
if (
  rawContractedRate !== null &&
  (typeof rawContractedRate !== 'number' ||
   !Number.isFinite(rawContractedRate) ||  // ← NEU
   rawContractedRate < 0)
) {
  return NextResponse.json({ error: 'Vertragssatz muss ≥ 0 sein' }, { status: 400 });
}

// extraHoursRate (Zeile 108) — gleicher Fix:
if (rawExtraRate !== null && (typeof rawExtraRate !== 'number' || !Number.isFinite(rawExtraRate) || rawExtraRate < 0)) {
```
