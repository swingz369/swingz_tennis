## Ziel

Mass-Migration der 287 un-force-dynamic API-Routes auf `export const dynamic = 'force-dynamic';` Marker in 3 Cluster-Sprints mit **Non-Blind-Script-Approach**: repository-konsistente Anchor-Detection, pro-Route Audit-Trail in `migration-log/`, Prettier-Formatierungs-Recovery, statische Routen-Listen für Re-Reproduzierbarkeit.

## Migration-Default (M1+M2 — Repo-Consistent)

Historisch falsch angenommene Spec ("ERSTE Zeile vor-imports" + Defensiv-Comment) wurde per Code-Reviewer Round-2 Polish Q1+Q2 verworfen. Korrekter Default basiert auf Empirik über alle existierenden force-dynamic-Konfigurationen:

- **Placement**: Zeile **direkt nach letzter Import-Deklaration** (in mehrzeiligen Import-Blöcken: an Ende des `} from '...'`-Statements). Das ist die Position, an der Next.js die Route-Segment-Config erwartet: vor globalen Modul-Consts (`const log = createLogger(...)`) und vor Handlern.
- **Whitespace**: Genau **1 Leerzeile nach `export const dynamic`** (= Abgrenzung zum nächsten Modul-Top-Element). Der Default-Block sieht also so aus:

  ```typescript
  import { withApiAuth } from '@/lib/api-auth';

  export const dynamic = 'force-dynamic';

  const log = createLogger('api:admin/...');
  ```

- **Kommentar**: **KEIN** Audit-Kommentar. Next.js-Segment-Config-Marker ist self-documenting. Die 65+ existierenden force-dynamic-Routes tragen **keinen** Kommentar — Bulk-Migration muss Stil-Konsistenz wahren, sonst Style-Erosion über 287 Files.
- **Reihenfolge bei mehreren Segment-Configs**: `dynamic` **zuerst**, dann `runtime`, dann `revalidate`, dann `fetchCache`. Wenn eine Datei bereits `export const runtime` hat, wird `dynamic` davor eingefügt.

## Risiken (Non-Blind-Approach-Begründung)

### Risiko 1: Blind-Sed-Regression

Ein blind-anwendbarer sed-Befehl würde 287 Routes verändern ohne dass die Tests einzeln die Verträglichkeit prüfen. **Daher: Node.js-Script mit expliziter Anchor-Detection (nicht sed).** Tests sind im per-Cluster ausgeführt, nicht global-coverage.

Beispiel für **BAD** (sed-only, CRITICAL-3 Code-Reviewer):

```bash
# NOT-DO: Findet alle blocker-routes, sed-inserts ohne Review
find app/api -name 'route.ts' | xargs sed -i '1i export const dynamic = '"'"'force-dynamic'"'"';'
# PROBLEMATISCH: 1) sed inserted vor-imports (non-conform), 2) keine Skip-Logik für
# bereits-konfigurierte Routes, 3) Defensive Comment enthält → Style-Drift
```

Beispiel für **GOOD** (Node.js mit Anchor-Detection):

```javascript
// scripts/force-dynamic-bulk-migration.mjs (extract)
function findInsertionPoint(lines) {
  // Rückwärts: letzte Zeile die zu einem Import-Block gehört
  for (let i = lines.length - 1; i >= 0; i--) {
    if (/^(import .*|} from .*|export type .*)$/.test(lines[i].trim())) {
      return { lineIndex: i, anchorType: 'post-import' };
    }
  }
  // Fallback: keine Imports gefunden → Insertion Zeile 1
  return { lineIndex: 0, anchorType: 'file-start' };
}
```

### Risiko 2: Force-Dynamic-Auf-Statische-Route

Falls eine Route aktuell `force-static` oder andere Annotation hat, würde der Insert die Original-Annotation überschreiben. **Detection-Pre-Apply (Skip-Condition 'manual-review-required')**: Script prüft ob `export const dynamic` bereits existiert via Regex `/export\s+const\s+dynamic\s*=/` UND ob force-static verwendet wird via Regex `/force-static/`. Wenn force-static erkannt → skip + warn.

### Risiko 3: Geistige-Bulk-PR-Size

Ein 287-File-PR ist review-unfreundlich. **Mitigation**: Cluster-Splits in 3 Sprints + jede-Sprint-PR <50-Files.

### Risiko 4: Style-Drift-durch-Audit-Comments

Wenn jede Sprint-1-Route einen Defensiv-Comment erhält, divergiert das Repo von 65/65-Konvention. **Mitigation (M1)**: kein Comment in Bulk-Migration; nur die ursprüngliche `/api/admin/approvals/count`-Sonder-Route (User-Blocker-Anchor aus TICKET 2.4.5) trägt den 1-Zeilen-Comment als Forward-Audit-Trail.
