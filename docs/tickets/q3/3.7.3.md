# 3.7.3 — `season_planning_history.action_type` CHECK-Constraint Whitelist-Mismatch

> **Epic:** 3.7 Backlog-Reconciliation · **Quartal:** Q3 · **Aufwand:** 0.5 h  \
> **Status:** ❌ TODO · _zuletzt geprüft: 2026-07-01_

## Ziel

Der Postgres-Check-Constraint `season_planning_history_action_type_check` (Error-Code `23514`) lehnt die vom AFTER-INSERT/UPDATE/DELETE-Trigger `log_season_plan_entry_changes()` emittierten `action_type`-Werte `created`, `updated`, `deleted` ab. **Konsequenz**: Jeder erfolgreiche `INSERT INTO season_plan_entries` löst den Audit-Trigger aus, der sein Insert in `season_planning_history` mit 23514 abbrechen lässt — die Logging-Tabelle bleibt leer, obwohl die Trigger-Logik korrekt geschrieben wurde.

Dieser Bug war vor 2026-06-30 durch den FK-Drift auf `season_plan_entries.group_id` (siehe `docs/decisions/20260630_recorrect_season_plan_entries_group_fk.sql`) **maskiert**: Die Cluster-Engine schlug bereits am FK-Insert (Code `23503`) fehl, der Trigger wurde nie erreicht. Nach dem FK-Fix rückt der 23514-Channel in den Vordergrund — `SeasonClusteringEngine.runClustering()` ist deshalb immer noch cluster-blockiert.

Akzeptanz-Effekt: Ein direkter `INSERT INTO season_plan_entries …` mit allen NOT-NULL-Spalten gefüllt wird **erfolgreich durchlaufen** und erzeugt einen Eintrag in `season_planning_history` mit dem passenden `action_type`.

## Symptom — exakte Fehlermeldung aus Live-DB-Repro

```
INSERT INTO season_plan_entries (
  season_id, club_id, trainer_id, day_of_week, start_time, end_time,
  duration_minutes, entry_type, planning_source, status
) VALUES (...)

→ Postgres Error:
   SQLSTATE:    23514      (check_violation)
   CONSTR_NAME: season_planning_history_action_type_check
   MESSAGE:     new row for relation "season_planning_history"
                violates check constraint "season_planning_history_action_type_check"
   DETAILS:     Failing row contains (…)
```

Die Live-Probe (siehe "Quellen / Beweise") bestätigt: derselbe Constraint blockt auch **direkte** Inserts in `season_planning_history` mit dem Wert `'created'`, `'updated'` oder `'deleted'`.

## Root Cause — drei Quellen, kein Konsens

| Quelle | Definiert / emittiert | Akzeptiert von CHECK? |
|---|---|---|
| **Live-Check-Constraint** (Whitelist-Probe 2026-07-01) | 11 Werte: `season_created`, `preferences_opened`, `auto_plan_started`, `plan_published`, `season_activated`, `season_completed`, `manual_edit`, `entry_added`, `entry_modified`, `conflict_resolved`, `preferences_closed` | ✅ |
| Trigger `log_season_plan_entry_changes()` in `supabase/migrations/20260506_fix_season_planning_groups.sql` L145-188 | INSERT → `created`, UPDATE → `updated`, DELETE → `deleted` | ❌ alle 3 rejected |
| Trigger `log_season_planning_action()` in `supabase/migrations/20260519_fix_season_planning_history_trigger_security_definer.sql` | INSERT/UPDATE auf `seasons` → `'season_created'`, `'preferences_opened'`, `'auto_plan_started'`, `'plan_published'`, `'season_activated'`, `'season_completed'`, `'manual_edit'` | ✅ alle 7 accepted |
| Spalten-Kommentar in `supabase/migrations/20260506_season_planning_system.sql` L220-222 | `'plan_created'`, `'plan_regenerated'`, `'entry_added'`, `'entry_modified'`, `'entry_removed'`, `'conflict_resolved'`, `'preferences_opened'`, `'preferences_closed'`, `'published'` | ❌ 4 rejected: `plan_created`, `plan_regenerated`, `entry_removed`, `published` |

**Drei verschiedene Wahrheits-Quellen, kein Schnittpunkt.** Die CHECK-Constraint-Whitelist wurde offenbar manuell aus dem Initial-Comment-Literal der Spalte L221 generiert, aber die Trigger-Funktionen wurden **separat** weiterentwickelt (in `20260519_*_security_definer.sql` wurde der Season-Trigger angepasst; in `20260506_fix_season_planning_groups.sql` wurde der Plan-Entry-Trigger komplett neu geschrieben), ohne die Whitelist zu erweitern.

**Konsequenz**: Die Trigger-Logik (`log_season_plan_entry_changes`) ist ***korrekt geschrieben*** und macht semantisch das Richtige — sie wird nur vom Constraint abgelehnt.

## Präventions-Hinweis (in den nachfolgenden Sessions als Forward-Spec pinnen)

Der Bug ist symptomatisch für ein größeres Pattern in `supabase/migrations/`:

1. **Mehrere Trigger-Funktionen auf derselben Tabelle** (`season_planning_history` hat aktuell 2: `log_season_plan_entry_changes` und `log_season_planning_action`), die **unabhängig voneinander** evolvieren.
2. **Spalten-Kommentar als implizite Doku** der CHECK-Whitelist, aber **keine CI-Verifizierung** dass COMMENT == LIVE-CONSTRAINT.
3. **Trigger-Code außerhalb der `supabase/migrations/`-Source-of-Truth** — `lib/season-planning/clustering-engine.ts` ruft den Trigger implizit über DML auf, hat aber keinen direkten Vertrag über `action_type`-Werte.

Empfohlene Folge-Tickets (separat, separat-priorisiert):

- **3.7.3-Folge A**: `ADR-007-whitelist-source-of-truth.md` — Kommentar-Literal als Single-Source-of-Truth definieren, CI-Gate das jede CHECK-Constraint-Whitelist gegen das Kommentar-Literal der Spalte driftet.
- **3.7.3-Folge B**: Trigger-Funktionen auf `season_planning_history` zu EINER `log_season_planning_event()` zusammenfassen (DRY-Prinzip, vermeidet Cross-Trigger-Drift).
- **3.7.3-Folge C**: Mock-freie Integration-Tests gegen Test-Containers-Postgres (analog Empfehlung in der 3.7.x-Präventions-Analyse — schließt 23503-/23514-Klassen von vorn herein aus).

**Konstruktions-Beweis der Diskrepanz**:

- **Trigger `log_season_plan_entry_changes()`** in `supabase/migrations/20260506_fix_season_planning_groups.sql` L145-188 (im Repo committed):
  ```sql
  IF TG_OP = 'INSERT' THEN
    INSERT INTO season_planning_history (..., action_type, ...)
    VALUES (..., 'created', ...);          -- ← rejected by live CHECK
  ELSIF TG_OP = 'UPDATE' THEN
    ...
    VALUES (..., 'updated', ...);          -- ← rejected by live CHECK
  ELSIF TG_OP = 'DELETE' THEN
    ...
    VALUES (..., 'deleted', ...);          -- ← rejected by live CHECK
  ```

- **Spalten-Kommentar** in `supabase/migrations/20260506_season_planning_system.sql` L220-222 (definiert die ursprüngliche CHECK-Whitelist als Doku):
  ```sql

                                          -- 'preferences_opened', 'preferences_closed', 'published'
  ```
  → Kommentar widerspricht dem **ausgeführten** Constraint, der nur 11 der 9 dokumentierten Werte zulässt (zuzüglich 5 vom `log_season_planning_action`-Trigger).
